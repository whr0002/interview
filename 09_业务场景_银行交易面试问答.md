# Banking Transaction Interview Q&A

## 中文版

### 问题 1：如果服务更新到一半，运行了十几分钟后又回滚，但期间已经处理了一些事务，系统应该怎么应对？

正式回答：

在这种场景下，我会先区分“代码回滚”和“业务回滚”这两个概念。服务版本可以回滚，但已经成功提交的业务事务通常不能依赖应用回滚来自动撤销，因为这些事务可能已经写入数据库、发送消息，或者影响了下游系统。因此，系统设计不能把发布回滚当成业务纠错的主要手段。

更合理的做法是从四个层面来应对。

第一，发布策略上要尽量降低风险，例如采用灰度发布、金丝雀发布或蓝绿发布，先让少量流量进入新版本，观察关键指标后再逐步放量。这样即使发现问题，影响面也可控。

第二，系统演进要保证兼容性。比如数据库变更尽量采用向后兼容的方式，新增字段而不是直接删除旧字段；消息体和接口字段也应允许新旧版本共存。这样在回滚时，旧版本仍然可以读取和处理新版本在那段时间内产生的数据。

第三，关键业务操作要具备幂等性、补偿能力和重试机制。幂等性可以避免回滚后重放消息、重复提交或任务补跑时造成重复扣款、重复入账。对于已经错误执行的业务，需要通过补偿事务或冲正交易来修复，而不是直接修改历史结果。

第四，需要有完善的对账和监控机制。因为现实系统中不可能完全避免中间状态，所以通常会通过实时监控、异常告警、定时对账和人工兜底流程来发现并修复问题，确保数据最终收敛到正确状态。

所以我的总结是：服务发布失败时，代码可以回滚，但业务上要依靠兼容性设计、幂等、补偿、重试和对账机制来控制风险，并保证最终一致性。

### 问题 2：对于跨多个事务、多个服务的一致性问题，现实中的银行一般是怎么处理的？

正式回答：

现实中的银行通常不会依赖一个覆盖所有系统的全局分布式强一致事务来解决问题，因为银行系统往往涉及核心账务、支付通道、通知、风控、报表和清算等多个子系统。如果把这些系统全部放进一个大事务里，会带来明显的性能、可用性和故障恢复问题。

银行更常见的做法是把“核心账务”和“外围系统”分开处理。对于账户余额、账务分录、总账这类核心账务，要求强一致，通常会在高度受控的账务系统内完成，确保每笔交易都有唯一流水号、完整分录和清晰的审计轨迹。对于通知、报表、风控同步等外围流程，则更多采用异步处理，接受短暂的不一致，但要求最终一致。

在实际实现上，银行非常依赖交易流水、幂等控制、冲正补账和对账机制。每一笔交易都会有唯一业务流水号，用于防重复、防乱序和问题追踪。如果某一步执行失败，通常不会简单删除历史记录，而是通过冲正或补账生成新的反向分录来修正结果，以满足审计和合规要求。

另外，银行还会大量使用日终对账、批量核对和异常挂账处理机制。因为跨系统调用中可能出现超时、重复、丢消息、对端已成功但本端未确认等情况，所以系统设计重点不是完全消灭中间状态，而是确保每一笔状态都可追踪、可核对、可补偿、可人工介入。

所以如果用一句话总结，现实银行处理多事务一致性的方式通常是：核心账务强一致，外围系统最终一致，再通过幂等、重试、冲正、补账和对账体系来保证整体业务可靠性。

## English Version

### Question 1: If a service is partially rolled out, runs for some time, and then gets rolled back after already processing transactions, how should the system handle that situation?

Formal answer:

In this scenario, I would first distinguish between rolling back code and rolling back business effects. The application version can be rolled back, but business transactions that have already been successfully committed usually cannot be undone simply by reverting the deployment. By that point, data may already be persisted in the database, messages may have been published, and downstream systems may already have acted on those events. For that reason, deployment rollback should not be treated as the primary business recovery mechanism.

A practical approach is to address the problem from four angles.

First, the release process should reduce blast radius through staged rollout strategies such as canary release, gray release, or blue-green deployment. That allows the team to detect abnormal behavior early and limit the number of affected transactions.

Second, the system should be designed for backward-compatible evolution. Database schema changes should usually be additive first, and API or message contracts should allow old and new versions to coexist temporarily. That makes rollback safer because the previous version can still read and process data produced by the newer version.

Third, critical business operations should be idempotent and support retries and compensation. Idempotency prevents duplicate charging or duplicate posting when requests are retried, messages are replayed, or jobs are rerun. If incorrect business actions were already executed, they should be corrected through compensating transactions or reversal entries rather than by directly mutating history.

Fourth, the system needs strong monitoring and reconciliation capabilities. In real production systems, temporary inconsistency is sometimes unavoidable, so monitoring, alerting, reconciliation jobs, and operational recovery processes are essential to detect issues and bring the system back to a correct final state.

So my summary would be: when a release fails, the code can be rolled back, but the business side should rely on compatibility, idempotency, retries, compensation, and reconciliation to control risk and preserve eventual correctness.

### Question 2: How do real-world banks usually handle consistency across multiple transactions and multiple services?

Formal answer:

In practice, banks usually do not rely on one large global distributed transaction across all systems. A banking environment typically spans multiple domains such as core ledgering, payment channels, notifications, fraud control, reporting, and clearing. Trying to enforce one strong transaction across all of them would create major problems in performance, availability, and recovery.

The more common approach is to separate core financial consistency from peripheral system consistency. Core ledger operations, such as balance updates, accounting entries, and general ledger posting, are handled with very strong consistency in tightly controlled systems. Each transaction is given a unique reference, complete accounting records, and a full audit trail. Peripheral capabilities, such as notifications, reporting, and some downstream synchronizations, are often handled asynchronously with an eventual consistency model.

At the implementation level, banks rely heavily on transaction references, idempotency controls, reversals, corrective postings, and reconciliation. Every transaction typically has a unique business reference to prevent duplication and support traceability. If a step fails, the system usually does not erase history. Instead, it records reversing entries or corrective transactions so that the financial and audit trail remains intact.

Banks also depend heavily on end-of-day reconciliation, batch verification, and exception handling processes. In cross-system communication, there can be timeouts, duplicate delivery, lost acknowledgments, or cases where one side succeeds but the other side has not yet confirmed it. Because of that, the design goal is not to eliminate every temporary intermediate state, but to ensure that every state is traceable, reconcilable, compensable, and recoverable.

So in one sentence, the real-world banking model is usually: strong consistency for core ledgering, eventual consistency for peripheral systems, and overall reliability ensured through idempotency, retries, reversals, corrective posting, and reconciliation.
